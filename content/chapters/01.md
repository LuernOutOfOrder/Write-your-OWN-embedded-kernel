## CPU privilege mode

So first thing first, our kernel run on a CPU, a chip, silicium. And CPU have privilege mode. On RISC-V there's 3 privilege mode:

M-mode(machine mode): highest privilege mode, everything is accessible. In some case, some kernel will not run on this privilege mode and will prefer to run on top of another software, like OpenSBI. But we will not use that, our kernel will run on this privilege mode.
In this mode we can:

- Access all CSRs.
- Configurate interruptions.
- Handle other privilege mode.
- Access hardware.

S-mode(supervisor mode): This privilege mode restrict access to hardware, such as physical memory and devices interruption.

U-mode(user mode): This is the lowest privilege mode, in this mode, you can't access directly to hardware, privileged CSRs, interruptions configuration. If a software running in U-mode need access to kernel services, like hardware access, the software will use an `ecall`, triggering a trap to higher privilege mode.

A higher privilege mode can access CSRs from lowest privilege mode, but a lower privilege mode can't access CSRs from higher privilege mode.

```
M-mode > S-mode > U-mode
```

So here's the CPU privilege mode. If you want to find more informations about them, refer to the References section.

## CSR

We talked about CSRs in the CPU privilege mode, but what's a CSR ? CSR mean `Control and Status Register`.
A CSR is a special register in RISC-V, they allow us to manage hardware configuration.

We access CSRs by using special RISC-V instruction. Every time we will access those CSRs, it will be from assembler instructions.

For example, in M-mode we can use the mstatus CSR. From the official RISC-V documentation: "The `mstatus` register keeps track of and controls the hart’s current operating state.". So we can for example enable or disable interruption using the `mstatus.mie` bit.
Another example is the `mhartid` CSR, it's also a M-mode CSR because it start with the M letter(so obvious), and it allow us to get the CPU core running the current code.

And because we are writing a kernel, we will use a lot of CSRs, like always.

## Binary file

If you already know how a binary file is composed, like sections etc, you can directly goto chapter 2!

So, what's in a binary file ? A binary file is made from multiple sections, each sections have a specific purpose.

`.text`: is the program’s actual code (the assembly). So every functions you are writing, will be stored in this section.
`.rodata`: read-only data, so all constant or static non-mutable variables will be stored here.
`.data`: read and write data, all initialized(non-zero), variables that can be modified are stored in this section.
`.bss`: all non initialized(zero) variables are stored here. Even if the variable is explicitly initialized, if it's initialized at `0`, it will be stored in this section. This section is actually not load in the binary, because it will take useless space. We just save the start and end address of this section, and load it in memory.

So for example, if we declare some variables:

```rust
// This variable is initialized with a non-zero value, but it's not mutable, so it will go to `.rodata` section.
let init_value: usize = 38;
// This variable is initialized with a non-zero value, and it's mutable, so it will be stored in the `.data` section.
let mut mut_init_value: usize = 12;
// This variable is not initialized, so it will be stored in the `.bss` section.
let uninit_value: usize;
// This variable is initialized, but at 0, so it will be stored in the `.bss` section too.
let almost_uninit_value: usize = 0;
```

Sections doesn't have the same privilege, some sections can be modified, some cannot.

`.text`: RO
`.rodata`: RO
`.data`: RW
`.bss`: RW

We can add some custom section to our binary, for example, when we will write our drivers, we will save every driver init function to a special section called `initcall`. Just like linux.

There's also other section like `.symtab`, where all symbols are saved. This section is strip(delete) from binary when using in release for example, to reduce binary size.

Symbols are used to know a function name for example.

## Linker file

To handle all binary section correctly, we use a linker file. This linker file allow us to define like how our binary will be linked.

The compiler already knows how to compile and store things in sections, but it cannot know where to put those sections; the linker file is here for that.  
In a linker file, we define where those sections will live in memory, how they are aligned, and whether they are loaded or not.

Linker file are not trivial to write at first, so here's how it's composed, and some syntax help.

```ld
/* Provide function entry point, just write the name of the function */
ENTRY()

/* Define memory region, like RAM, ROM, FLASH, etc. Because at first, the kernel will run on qemu-system-riscv32, using the virt machine, we will simulate ROM by just using RAM. Just separate the two of them */
MEMORY {
  RAM (rwx) : ORIGIN = ..., LENGTH = ...
  /* Not real ROM or flash from qemu virt machine, just use another RAM region to simulate real hardware behavior */
  ROM (rx) : ORIGIN = ..., LENGTH = ...
}

/* Define all binary sections */
SECTIONS {
  /* Set origin for ROM Memory region */
  . = ORIGIN(ROM);
  /* Provide kernel image start symbol */
  kernel_start = .;

  /* Each section is defined like that */
  .text {
   /* Here we can define what's in the section, and provide symbol*/
   ...
  } > /* Here we define where to load the section in Memory Region (ROM or RAM in this context)*/

  /* make sure the symbols are provided to the symbol table */
  PROVIDE(__global_ptr = global_ptr);
  PROVIDE(__stack_start = stack_bottom);
  PROVIDE(__stack_top = stack_top);
  PROVIDE(__bss_start = bss_start);
  PROVIDE(__bss_end = bss_end);
  PROVIDE(__data_la_start = data_la_start);
  PROVIDE(__data_start = data_start);
  PROVIDE(__data_end = data_end);
  PROVIDE(__kernel_start = kernel_start);
  PROVIDE(__kernel_end = kernel_end);

  /* Debug info, in debug mode we want to keep all debug info available. */
  .debug_info     0 : { *(.debug_info) }
  .debug_abbrev   0 : { *(.debug_abbrev) }
  .debug_aranges  0 : { *(.debug_aranges) }
  .debug_line     0 : { *(.debug_line) }
  .debug_str      0 : { *(.debug_str) }
  .debug_loc      0 : { *(.debug_loc) }
  .debug_ranges   0 : { *(.debug_ranges) }
  .debug_macinfo  0 : { *(.debug_macinfo) }
}
```

So now the goal is to write the linker file for our machine, we will use the `virt` from `qemu-system-riscv32`, so we need to define all binary section:

- `.text`
- `.rodata`
- `.data`
- `.bss`
- `.stack`

Writing a linker file can be painful; you can find some reading in the References section at the end of the chapter.

There's some section that you don't want to load into your binary. "Why ?" you'll ask me. Because some section will just take too much space for nothing. Best example is the `.bss` section, this section only contain zero, so why load it into our binary ? We just want to keep symbol for the start and end of the `.bss` section, and our bootloader will just fill a region in memory with zero. The `.stack` section too, we don't want to load it into our binary.

So if we don't load those sections in our binary, how does the kernel know where to find the .bss section or the stack ? A binary contains symbols; symbols are like label, names, for function names or address location. And in our linker file, in the .bss section, we define symbols for the start and end of the section, so we can just use, for example, the `__bss_start` symbol, and it will give us directly the .bss start address.
