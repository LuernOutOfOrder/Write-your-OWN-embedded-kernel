## CPU privilege mode

So first thing first, our kernel run on a CPU, a chip, silicium. And CPU have privilege mode. On RISC-V there's 3 privilege mode: 

M-mode(machine mode): lowest privilege mode, everything is accessible. In some case, some kernel will not run on this privilege mode and will prefer to run on top of another software, like OpenSBI. But we will not use that, our kernel will run on this privilege mode.
In this mode we can:
- Access all CSRs.
- Configurate interruptions.
- Handle other privilege mode.
- Access hardware.

S-mode(supervisor mode): This privilege mode restrict access to hardware, such as physical memory and devices interruption.

U-mode(user mode): This is the highest privilege mode, in this mode, you can't access directly to hardware, privileged CSRs, interruptions configuration. If a software running in U-mode need access to kernel services, like hardware access, the software will use an `ecall`, triggering a trap to lowest privilege mode.

A lowest privilege mode can access CSRs from highest privilege mode, but highest privilege mode can't access CSRs from lowest privilege mode. 

```
M-mode > S-mode > U-mode
```

So here's the CPU privilege mode. If you want to find more informations about them, refer to the References section.

## CSR

We talked about CSRs in the CPU privilege mode, but what's a CSR ? CSR mean `Control and Status Register`.
A CSR is a special register in RISC-V, they allow us to manage hardware configuration. For example, in M-mode we can use the mstatus CSR. From the official RISC-V documentation: "The `mstatus` register keeps track of and controls the hart’s current operating state.". So we can for example enable or disable interruption using the `mstatus.mie` bit.
Another example is the `mhartid` CSR, it's also a M-mode CSR because it start with the M letter(so obvious), and it allow us to get the CPU core running the current code. 

And because we are writing a kernel, we will use a lot of CSRs, like always.

## Binary file

If you already know how a binary file is composed, like sections etc, you can directly goto chapter 2!

So, what's in a binary file ? A binary file is made from multiple sections, each sections have a specific purpose. 

`.text`: is the program’s actual code (the assembly). So every functions you are writing, will be stored in this section.
`.rodata`: read-only data, so all constant or static non-mutable variables will be stored here.
`.data`: read and write data, all initialized(non-zero), variables that can be modified are stored in this section.
`.bss`: all non initialized(zero) variables are stored here. Even if the variable is explicitly initialized, if it's initialized at `0`, it will be stored in this section. This section is actually not load in the binary, because it will take useless space. We just save the start and end address of this section, and load it in memory. 

Sections doesn't have the same privilege, some sections can be modified, some cannot.

`.text`: RO
`.rodata`: RO
`.data`: RW
`.bss`: RW

We can add some custom section to our binary, for example, when we will write our drivers, we will save every driver init function to a special section called `initcall`. Just like linux.

There's also other section like `.symtab`, where all symbols are saved. This section is strip(delete) from binary when using in release for example, to reduce binary size.

Symbols are used to know a function name for example.

## Linker file

To handle all binary section correctly, we use a linker file. This linker file allow us to define like how our binary will be compiled.

Linker file are not trivial to write at first, so here's how it's composed, and some syntax help.

```ld
/* Provide function entry point, just write the name of the function */
ENTRY()

/* Define memory region, like RAM, ROM, FLASH, etc. Because at first, the kernel will run on qemu-system-riscv32, using the virt machine, we will simulate ROM by just using RAM. Just separate the two of them */
MEMORY {
  RAM (rwx) : ORIGIN = ..., LENGTH = ...
  /* Not real ROM or flash from qemu virt machine, just use another RAM region to simulate real hardware behavior */
  ROM (rx) : ORIGIN = ..., LENGTH = ...
}

/* Define all binary sections */
SECTIONS {
  . = ORIGIN(ROM);
  /* Provide kernel image start */
  kernel_start = .;

  .text : {
    /* Custom section for asm init */
    *(.text.init)
    *(.text*)
  } > ROM

  .initcall : {
    __initcall_start = .;
    KEEP(*(.initcall))
    __initcall_end = .;
  } > ROM

  global_ptr = .;

  .rodata : {
    *(.rodata*)
  } > ROM

  . = ORIGIN(RAM);

  .data : {
    data_start = .;
    *(.data*)
    data_end = .;
  } > RAM AT > ROM
  data_la_start = LOADADDR(.data);

  /* Don't write .bss section in bin file */
  .bss (NOLOAD) : {
    bss_start = .;
    *(.bss*)
    /* Avoid any global uninitialized variable to be saved in another section */
    *(COMMON)
    bss_end = .;
  } > RAM

  /* Provide kernel image end */
  kernel_end = .;

  /* Stack */
  /* Don't write stack section in bin file, just reserve the memory in the RAM */
  .stack (NOLOAD) : ALIGN(4) {
    /* stack starts at RAM top */
    stack_top = ORIGIN(RAM) + LENGTH(RAM);
    /* 0x4000 = 16 KiB */
    stack_bottom = stack_top - 0x2000;
  } > RAM

  /* make sure the symbols are provided to the symbol table */
  PROVIDE(__global_ptr = global_ptr);
  PROVIDE(__stack_start = stack_bottom);
  PROVIDE(__stack_top = stack_top);
  PROVIDE(__bss_start = bss_start);
  PROVIDE(__bss_end = bss_end);
  PROVIDE(__data_la_start = data_la_start);
  PROVIDE(__data_start = data_start);
  PROVIDE(__data_end = data_end);
  PROVIDE(__kernel_start = kernel_start);
  PROVIDE(__kernel_end = kernel_end);

  /* Debug info, in debug mode we want to keep all debug info available. */
  .debug_info     0 : { *(.debug_info) }
  .debug_abbrev   0 : { *(.debug_abbrev) }
  .debug_aranges  0 : { *(.debug_aranges) }
  .debug_line     0 : { *(.debug_line) }
  .debug_str      0 : { *(.debug_str) }
  .debug_loc      0 : { *(.debug_loc) }
  .debug_ranges   0 : { *(.debug_ranges) }
  .debug_macinfo  0 : { *(.debug_macinfo) }
}
```
