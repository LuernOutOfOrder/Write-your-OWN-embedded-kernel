So, in the `previous chapter`, we worked on the `bootloader`. Once our `kernel image` is `loaded` into `memory` and the kernel starts, what do we do?

## Early device initialization

Yeah, that's right, that's the part where we start talking about drivers.
`Drivers initialization` is a part of the `kernel boot process`. Without it, the kernel can't work.
We don't have a `console` yet, so we `can't print` anything. Print needs to use a `serial device` or `UART`. To print, we need at least a UART driver; we don't need all the operating system layer. That's our first step, `making` an `UART driver` so we can `print` and `debug`.

### What's a driver?

A `driver` is `software` that can allow `another software` to `interact` with a `physical device`, or, from Wikipedia: "A device driver is software that operates or controls a particular type of device that is attached to a computer. A driver provides a software interface to hardware devices, enabling other software to access hardware functions without needing to know precise details about the hardware.”.

We won't deal with `discoverable buses` such as `PCIe` or `USB`. Our devices are directly memory-mapped into the SoC address space, or the `MMIO`.

### MMIO

And what's that? `MMIO` (Memory-Mapped Input/Output) is a mechanism that maps `device registers` into the `physical address space`. Each device `occupies` a specific `memory region`, allowing the CPU to `communicate` with `hardware` using `ordinary memory accesses`.

On `MCU`, all devices are `built-in` the `SoC` (System on Chip). Their logic answers come from the `SoC internal bus`. `MMIO addresses` are just `routes` in the `SoC bus`.

### How do we write drivers?

Writing `drivers` is not as difficult as you think(maybe), the main logic to write a driver is very trivial: At their core, MMIO drivers communicate with hardware by reading and writing device registers. The difficult part is understanding the device documentation and knowing which registers to access and in what order.

### UART

We are working on the `qemu-system-riscv32 virt machine`. We can get a hardware description from the machine source code: [qemu/hw/riscv/virt.c at master · qemu/qemu · GitHub](https://github.com/qemu/qemu/blob/master/hw/riscv/virt.c).

If we look at this source code, we can see:

```c
static const MemMapEntry virt_memmap[] = {
    [VIRT_DEBUG] =        {        0x0,         0x100 },
    [VIRT_MROM] =         {     0x1000,        0xf000 },
    [VIRT_TEST] =         {   0x100000,        0x1000 },
    [VIRT_RTC] =          {   0x101000,        0x1000 },
    [VIRT_CLINT] =        {  0x2000000,       0x10000 },
    [VIRT_ACLINT_SSWI] =  {  0x2F00000,        0x4000 },
    [VIRT_PCIE_PIO] =     {  0x3000000,       0x10000 },
    [VIRT_IOMMU_SYS] =    {  0x3010000,        0x1000 },
    [VIRT_PLATFORM_BUS] = {  0x4000000,     0x2000000 },
    [VIRT_PLIC] =         {  0xc000000, VIRT_PLIC_SIZE(VIRT_CPUS_MAX * 2) },
    [VIRT_APLIC_M] =      {  0xc000000, APLIC_SIZE(VIRT_CPUS_MAX) },
    [VIRT_APLIC_S] =      {  0xd000000, APLIC_SIZE(VIRT_CPUS_MAX) },
    [VIRT_UART0] =        { 0x10000000,         0x100 },
    [VIRT_VIRTIO] =       { 0x10001000,        0x1000 },
    [VIRT_FW_CFG] =       { 0x10100000,          0x18 },
    [VIRT_FLASH] =        { 0x20000000,     0x4000000 },
    [VIRT_IMSIC_M] =      { 0x24000000, VIRT_IMSIC_MAX_SIZE },
    [VIRT_IMSIC_S] =      { 0x28000000, VIRT_IMSIC_MAX_SIZE },
    [VIRT_PCIE_ECAM] =    { 0x30000000,    0x10000000 },
    [VIRT_PCIE_MMIO] =    { 0x40000000,    0x40000000 },
    [VIRT_DRAM] =         { 0x80000000,           0x0 },
};
```

In this array, we can see the `VIRT_UART0` device; this is the `device` we want to write a `driver` for. We now have the `MMIO address` and the `size` for this device.

On the `qemu-system-riscv32 virt machine`, the `VIRT_UART0` is an `ns16550` compatible `UART`. So if you want information about the `ns16550` device, you can find easily.

To write to the `UART device`, we just need to write to the `UART device address`. In `Rust`, we are doing that with the `core::ptr` module.

```rust
unsafe{
 core::ptr::write_volatile(VIRT_UART0_address, b)
}
```

We can only write one byte at a time to the UART device, so if we want to write a string, we must break it down into characters in a loop.

#### Write volatile

Why use write volatile instead of just a `ptr::write`? When using a simple `write`, the `compiler` can `optimize` the write operation. There's plenty of optimization the compiler can do, and we want none of it.

Volatile accesses tell the compiler that every read or write matters and must be emitted exactly as written. The compiler must not remove or merge these operations, since interacting with hardware produces side effects that ordinary memory accesses do not have.

#### What's a UART?

A `UART` is a serial protocol used to exchange serial data between two devices. `UART` is `asynchronous`, both `transmitter` and `receiver` do not share a common clock signal. The `transmitter` and `receiver` must transmit at the `same pre-arranged speed` in order to have the `same bit timing`. Most common `UART` baud rates in use today are `4800`, `9600`, `19.2K`, `57.6K`, and `115.2K`.

#### Ns16550

There are multiple registers that are important for this device, but now, we just want to set the `word length to 8 bits`, `enable FIFO` and `enable receiver interrupts`.

The word length describes how many bits a UART frame will contains. We set it to 8 bits because it's the standard to transfer bytes. Both sides must have the same word length.

We enable the FIFO so we don't only have one register to store data. Without it, if the CPU doesn't read the byte before the next one come, we will lose it. With FIFO multiple bytes can be stored in a FIFO(16 bytes on the ns16550)

Enabling receiver interruptions means that when data is added to the receiver, the CPU will know through an interruption. If we don't enable the receiver interruption, and still want to read incoming data, we need to read the receiver in a loop, and waste CPU cycle.

### Print abstraction

Earlier, we talked about what a driver is, and a driver provides an interface for other software to interact with the underlying device without knowing anything about the device itself. But how do we do that ?

Well, your choice, you can either use Rust `traits` to provide an interface, implement it to your `driver`, and create a global pointer, using `dyn trait`, so you just have to call your pointer, use the trait methods, and use the driver behind it.

You can do the same thing, but with a bigger abstraction using a `subsystem`. This is a bigger abstraction, usually used to handle multiple devices of the same type. This kind of implementation depends on you.

### How to initialize devices at runtime?

That's an interesting part, because we are on embedded hardware, and we have `two choices` for this.

#### Static initialization

We are defining the devices `statically`, so we know, at `compile-time`, what devices we will have and which `drivers` will be used.  
This is the `most used` way on embedded devices. Because we are on `small hardware`, we don't have the `Device Tree`.

#### Device tree

The `device tree` is a special file used to describe the devices on hardware. The `qemu-system-riscv32 virt machine` we are using has a `device tree`. This file is made to be parsed early in a kernel boot so we can get all hardware descriptions easily and early.
This is so cool because we just have to parse this file, and we can know everything about our hardware and initialize the correct drivers.

#### Which one to use?

Well, as I said in the `Static initialization` part, we are on embedded devices, so most of the embedded platforms don't have device tree.

So either you don't bother yourself at all and do everything in `static`, or you only use the `device tree`, even if using only the device tree is not the best idea. If you don't have a device tree, you can't initialize your devices.  
Or you can do both; but depending on your goals, you may introduce a `HAL`(Hardware Abstraction Layer) to abstract platform-specific details and device discovery mechanisms.

```rust
let device_info = platform_get_device_info("ns16550a");
```

This function will return the device information that is compatible with the driver `ns16550a`, without you knowing if the information came from the `device tree`, or `static definition`, depending on the nature of your `HAL`(using both device tree and static definition or not).
