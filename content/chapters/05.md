## What's an interrupt?

An interrupt is an `asynchronous` trap, meaning that something outside of the `currently` executing `instruction` caused the CPU to `trap`. 

There are some causes of an interrupt; for example:

- `timer interrupt`: a hardware clock that counts ticks and, when it reaches zero or a set limit, triggers an electrical signal to the CPU. The CPU will pause its current work, enter machine mode, and jump to a defined function. It's a timer interrupt.
- `software interrupt`: a signal generated internally by defined software will cause the CPU to pause its current work, enter machine mode, and jump to a defined function. It's a software interrupt.
- `external interrupt`: a signal generated from hardware, outside the processor core, forcing the CPU to pause its current work and enter machine mode, jumping to a defined function. It's an external interrupt.

Interrupt are the most used traps, except if your kernel enters a lot of error states and causes exceptions.

## What's an exception? 

An exception is a `synchronous` trap, meaning that the `currently` executing `instruction` caused the `trap`.  
It can be caused by an `illegal instruction`, an `instruction address misaligned`, a `breakpoint`, or anything from the `current running instruction`.

It's generally an `error` from the `program`. Like trying to `dereference` a `misaligned address`. 

So, now that we know more about `traps`, `asynchronous and synchronous`, and what an interrupt and an exception are, how do we use them?

## The RISC-V interrupt system

We already know from `Chapter 2` that the RISC-V ISA contain `CSR(Control and Status Registers)`.  
The interrupt system uses some of them, but we will mainly use `2` of them for this chapter.

- `mtvec(Machine Trap Vector)`: stores the `trap mode` and an `address` to a `function`. Whatever happens, the `CPU` will call the function given by this register. The `mtvec` CSR has `2 fields`; the `BASE` field contains the function address, and the `MODE` will define how the CPU will handle traps. MODE can be set to `direct or vectored`; direct mode means that all traps go to the same function. The vectored mode means that traps go to different functions based on the trap cause.
- `mcause(Machine Cause)`: contains the `exception code` to explain why a trap occurred. There are also `2 fields`; the `INTERRUPT` field contains the type of traps, either `synchronous or asynchronous`. It's the `most significant bit`, so we just need to do a bit mask to know. The second field is the `EXCEPTION CODE`, containing the trap reason.

And that's it; that's how the RISC-V interrupt system works, beautiful, isn't it? But now, how do we use them?

## Handle traps

### Save registers

First things first, when we enter a trap, we want to `store` all the `registers`. We don't want to mess with them, or we will never be able to `restore` a `task` in the near future.

So how do we do that? 

We can define a `structure in Rust` to do that; we will need:

- Store all general purpose register, we have 32 registers of 1 word in length. 
- Store the current pc(Program Counter)
- Use the #[repr(C)] directive so our structure follows the C-style structure. This is used so we can know our structure offset and handle them in assembly functions.

We will call our structure TrapFrame, so we know what we are talking about when mentioning it.

And that's it, for now.

We can use the mscratch(Machine Scratch) CSR to store a pointer to our structure. 

So we need to define a Rust function that will save our structure in the mscratch register in the kernel boot process, so when a trap occurs, we can use it.


### Trap in direct mode

#### Enter a trap

So, we know that the `mtvec` CSR contains our `trap handler function`. So we will at first be tempted to write our trap handler function in `pure Rust` and store the address of the function in `mtvec`; well, I don't think it's the best idea(with my XP, obviously). We would prefer to store a `trap entry function in asm`. 
But why? Well, because it's easier for `context switching` around the trap handler `in pure assembly`.  
Using `pure assembly` for `prologue and epilogue` around the trap handler function in Rust allows us to have `complete control` over which `registers` will be used. And in this `context`, it's like so important because when entering a trap, we `don't` want to `touch registers`. Why? Because imagine you are running a task, and BAM a trap occurred, like a timer interrupt. So you enter the trap, and all registers, the stack, and everything are set for your current task, so if you modify any of them and save them, when you return to your task, it will be corrupted, because if even one of the registers is corrupted, your system will be unstable.

So you want an `asm function` that will `save the current context`, `store` all `registers` inside the `TrapFrame`, and switch to a `dedicated stack`, and, just after that, you can call your `Rust function` to handle the trap correctly. And all of this, `without overriding any registers`.

#### Resolve a trap

So, you are now in your `Rust function`, nice. What now? Well, you already know the `2 registers` used in a `trap`; you already used `mtvec` for trap mode and stored the trap function entry point. So now you need to use `mcause`. This `CSR` contains the `type of trap` (interrupt or exception) and the reason. 

So you need to do a bit mask to extract the most significant bit(31 on 32 bits arch). After that, we want to do a second mask; we just want to keep the 30 remaining bits to know the trap reason. So we just do a mask to keep all bits except the most significant one.

After that, you can use both cause and reason to handle possible exceptions or interrupts.

One way to do that is by creating functions to handle exceptions and interrupts, passing the reasons to both of them, and using a match again to handle the trap reasons. 

Have it your way.

#### Exit a trap

After `handling the trap`, you'll `exit` your `Rust function` and continue execution in the `assembly trap entry` function.  
There you'll want to do the `same thing` as the `trap entry`, but in the `other way`. You want to `restore all registers` saved in TrapFrame, and switch back your `stack pointer` to your `task stack`.  
I talk about tasks, but we haven't seen them yet. That's just to make you understand that once your system starts its runtime, you'll run tasks, and traps will happen. During the kernel boot process, you'll disable traps. So you shouldn't enter a trap during the kernel boot process.

Once you have restored all the registers and switched back to your task stack, you can return from this function, and you should continue the task execution normally.

Here's a diagram of how to handle trap in direct mode basically:

```
Trap has been triggered
	|
	v
	mtvec
	|
	v
	trap entry function in asm:
	|
	v
	Save all registers without overriding any of them
	|
	v
	Entering main trap handler function in Rust
	|
	v
	Handler exception or interrupt by checking mcause
	|
	v
	Trap has been handle, exit Rust function
	|
	v
	Returning in the trap entry function in asm:
	|
	v
	Restore all previously saved registers
	|
	v
	Return from the trap entry function in asm(using mret, because we are currently running the kernel in machine mode, and we wan't to be able to restore mstatus fields and mepc).
```

Hey, what about `restoring` the `mstatus` field using `mret`? Oh, you read that? Great, to be `able to use traps` on `RISC-V`, you need to `enable mstatus.mie` bit, `mie` meaning `Machine Interrupt Enable`.  
When the `CPU` `enters a trap`, it will `automatically` set `mstatus.mie` to `0` and save the previous `mstatus.mie` value into `mstatus.mpie`(Machine Previous Interrupt Enable). And when you use `mret`, the `CPU` will `restore` `mstatus.mie` using the `value stored` in `mstatus.mpie`.
Same thing for `mepc`. When a trap occurs, the `CPU` `automatically` stores the current `Program Counter` into the `mepc` CSR. Later, when executing `mret`, the `CPU` resumes execution from the address stored in `mepc`.

### Trap in vectored mode

#### Resolve a trap

Entering a trap in `vectored mode` is `different` than `direct mode`; the goal of the `vectored mode` is to have a `function` that will act like a `jump table`.

The `CPU`, when entering a trap in `vectored mode`, will check the `trap type`; if it's an `exception`, the `CPU` will jump to the address in `mtvec`, and that's it.  
If the trap is an `interrupt`, the `CPU` will jump to the address in `mtvec + 4 x trap cause`.

What does that mean? It means that your function will be a jump table, so you just have a function where the only instruction is a jump to a dedicated function to handle the trap.

So if it's an exception, the `CPU` will jump to the address stored in `mtvec`; let's call it `BASE_ADDR`. The first thing this function should do is to jump to a dedicated function to handle exceptions from vectored mode. 

If it's an interrupt, the CPU will jump to `BASE_ADDR + 4 x cause`, so it will jump over the instruction to jump to the exception handler, and go to the instruction that should jump to the dedicated function used to handle this type of interrupt.

Yeah, that's a little confusing, but it's really elegant I think. The tricky part is that, you don't have the same prologue when entering a trap.
Because the CPU will jump directly to the instruction from `BASE_ADDR + 4 x cause`. So you can't write a prologue that will always be run when entering a trap in vectored mode.
So how can you save all registers etc like in direct mode ?
One way to do that is by writing an assembly macro that wrap the instructions to save context. Same thing to restore a context. 
You could call those macro in each dedicated function that are used for specific interrupts, and the one used for exceptions.

Then from thoses dedicated functions, you can call a rust function handling the trap.

Vectored mode for trap can be confusing, once you'll have an implementation you can see, it'll all make sense I promise.

A small diagram to see how vectored mode work:

```

 v
BASE
 |
 +0   j exception_handler
 +12  j software_interrupt
 +28  j timer_interrupt
```
