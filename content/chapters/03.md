## What’s a bootloader?

A bootloader is one of the first pieces of software to run on a machine. Its role is to set up the environment and load the kernel into memory so it can run.  
That’s it: a bootloader is very basic at its core; it only sets the hardware, like CPU privilege mode, handles some CSRs on RISC-V, loads the kernel into memory, and jumps to the kernel entry point.

## Writing a basic bootloader for RISC-V 32 bits

### Our basic bootloader

At first, we will write a basic bootloader but inside the kernel. Let me explain: a real bootloader is a single binary; a kernel is a single binary too. When the bootloader is run, it will find the kernel image and parse it using elf. And then it will load each section into memory and jump to the kernel entry point.

We will not do that, not at first.  
We will write our bootloader at the beginning of our kernel. So we will have just one binary. Our bootloader will know each section from its symbols, and it could load each section into its respective memory address.

### What’s first ?

#### Entry point

So, first things first, our bootloader needs to be the first thing to start on our machine; to do that, we need to define our `entry point`; we talk about that in `Chapter 1`. We define our entry point in our `linker file`, like that: `ENTRY(bootloader_start_fn)`. With that, when we link our binary, the entry point will be saved in it.

#### Flashing our binary

That part depends on `which environment` you want to run your kernel.  
For a start, using `QEMU` is good enough.  
For our kernel targeting `RISC-V 32 bits`, we will use `qemu-system-riscv32`, with the `virt machine`.  
To run `QEMU` with your binary, you can use this command:

```
qemu-system-riscv32 -machine virt -m 8 -nographic -bios none -kernel $(path_to_kernel_binary) 
```

By passing `none` to the `-bios` flag, we ensure that no bootloader will be used, only our kernel.

With that command, you’ll run your kernel inside QEMU.

Flashing a binary on real metal, like an `ESP32`, will be explained in a future chapter.

#### Bootloader structure

Our bootloader will be defined like that:

```S
# Disable generation of compressed instructions.
# Only use 32 bits instructions
.option norvc

# Define a .data section.
# Symbol in .data section
.section .data

# Define a .text.init section.
# Code in .text.init section
.section .text.init

# Define kstart function
.global bootloader_start_fn
.type bootloader_start_fn, @function
# Do not allow interrupts while running kinit
bootloader_start_fn:
 # Load everything in memory.
 ...
 # Once done, jump to the kernel entry point function in rust.
 # Not a real jump, we use `mret` instruction to continue execution using `mepc`
 # _start is rust kernel function entry point symbol 
 la t1, _start 
 csrw mepc, t1
 mret
```

That's what the bootloader function looks like, without the bootloader part, obviously, because YOU will write it.

### Loading binary in memory

#### LMA/VMA

To understand what we are doing here, it's important to understand the notion of `LMA/VMA`.

- `VMA(Virtual Memory Address)`: the address where a section is used at runtime. The linker uses the VMA to resolve symbols; for example, if we create a variable `int x = 67`, when the compiler generates code referencing `x`, it will encode the address of `x` in `RAM`.
- `LMA(Load Memory Address)`: the address where bytes are `physically stored` in the binary image. Where `data "sleeps"` in `flash` before being `copied` into `RAM`.

When we write in a linker file:

```ld
>RAM AT>ROM
__some_sym = LOADADDR(.some_section)
```

We tell the linker, "Resolve the symbols using `VMA` addresses(RAM), but store those bytes at the `LMA`(ROM)."

The `LOADADDR` function from the linker file is used to get the LMA from a section to make a symbol. That's what we will use for the .data section.

#### How to load our binary in memory

In order to be able to load our binary into memory, we first need to set up the environment; here's what we need to do:

- Set the `global pointer` using a `symbol` from the `linker file`.
- Set the `stack pointer` using a `symbol` from the `linker file`.

After that, we can start loading our binary into memory:

- Load the `.data` section into memory.
- Load the `.bss` section into memory.

And then, we update the `mstatus` `CSR` to ensure that we are in M-mode.

Then you can use `mret` to start the kernel from its entry point.

#### Some tips

Here are some tips and other information to be sure to do things correctly:

When we copy the `.data` section or fill the `.bss` section, we are doing that word by word. Why word by word and not byte by byte ? To keep it simple, we are using words because we are fully using the `memory bus`, the linker `guarantees symbol alignment`, and simple loop without exceptions to handle.

When we are running our binary, who calls the bootloader entry point ? On QEMU, it's QEMU itself who load the binary into memory and jumps to the ELF entry point.

Why using `mret` and not a simple `j` instruction ? We are using `mret`, so the update we are doing on `mstatus` is used, and we can jump to the kernel start function address saved in `mepc`. `mret` will update the machine mode using `mstatus.MPP` and the interruption status using `mstatus.MPIE`; then it will continue execution by jumping to the address stored in `mepc`.

- Before setting the `global pointer`, use `.option push` and `.option norelax`. Using `.option norelax` prevents the **linker** from assuming that `gp` is already initialized and replacing instructions with `gp`-relative versions. Without it, the linker relaxation would create a circular dependency when loading `gp` itself. See [RISC-V-Directives (Using as)](https://sourceware.org/binutils/docs-2.31/as/RISC_002dV_002dDirectives.html#RISC_002dV_002dDirectives)
- Before setting the `stack pointer`, use `.option pop`. See [RISC-V-Directives (Using as)](https://sourceware.org/binutils/docs-2.31/as/RISC_002dV_002dDirectives.html#RISC_002dV_002dDirectives)
- To load the `.data` section correctly, you’ll need `3 symbols` (`__data_start` and `__data_end`); that’s the destination for the `.data` section. And `__data_la_start`, the source, where the `.data` is saved in the binary. We can use a basic loop using branch to do a memcpy from source to destination.
- The `.bss` section is not something to really load into memory; we just need 2 symbols(`__bss_start` and `__bss_end`); they are both the destination for the `.bss` section; we just need to fill this region with 0. We can do a similar loop using branch than the loop used to load the `.data` section.
- Set `mstatus.MPP` to `M-mode`.
